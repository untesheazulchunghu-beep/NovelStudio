# 中长期规划

本文档记录短期规划之后的方向，形式参考 `ck/NovelForge-main/后续规划.md`：**方向先公开，不承诺具体发布时间**，排期随短期规划的完成情况与实际使用反馈调整。
问题背景见 [需要改进的内容](./需要改进的内容.md)，近期安排见 [短期规划](./短期规划.md)。

## 当前进度基线

- 已完成短期可靠性与工程底线：演示模式自动写入保护、批量相邻章节承接、章节级失败隔离与重试、会话吊销、模型错误分类、任务事件批量写入、TXT/Markdown 导出、本地草稿恢复与冲突确认、前端六块拆分、字数与工作流连线测试、ESLint/Prettier、CI，以及 MIT `LICENSE` 与 git 仓库。
- 短期明确不做、留在本文的方向：全量 RAG、多供应商、按节点选模型、结构化角色表、连续性检查、DOCX/EPUB、段落级提案采纳、协同编辑、原生移动端、配额与 OpenAPI。章节摘要与伏笔注入已在 M1 落地，节点级工作流执行已在 M2 落地，按关键事件逐条核对的审稿清单已在 M3 落地。
- 兼容说明：新增任务会保存可重试的请求快照；升级前的历史任务没有快照，无法自动恢复。

- **中期**：短期规划完成后的下一阶段，目标是让长篇创作「写得准、管得住」。
- **长期**：产品形态与生态层面的探索，需要中期能力作为基础。

## 总体路线

```
短期：可靠（不丢稿、不误写、可恢复、有测试）
  └─ 中期：更准（上下文检索、连续性检查、多模型；节点级工作流已在 M2 完成，关键事件审稿清单已在 M3 完成）
       └─ 长期：更广（协作、多格式、插件、部署形态）
```

## 中期规划

### M1. 章节摘要与长篇记忆（已完成）

- 状态：已实现。应用提案或自动写入后，用当前生成器写出「摘要 + 出场人物 + 新增设定 + 伏笔变化」并覆盖该章的当前记录。手动编辑或恢复正文版本后，来源版本不匹配的记忆会从生成上下文和伏笔投影中排除；作者可按需刷新。旧数据库无法证明已有记忆对应哪个正文版本，升级后标为待刷新。未应用的提案和未确认的演示生成不写记忆。
- 生成上下文：近 8 章摘要（宽于上一章结尾 600 字，也不再把 50 章以上的摘要全部塞进提示词）、蓝图点名的人物与地点及其关系（不再按 kind/label 取前 80 个实体和前 160 条关系）、以及仍未回收且与这些人物或地点相关的伏笔。已回收伏笔不再当作未回收注入。
- 上下文预算：`CONTEXT_BUDGET_RUNES`（默认 12000 字）均分给摘要、相关图谱和未回收伏笔，某一部分超长不会占掉其他部分的额度。任务详情记录注入项和未注入项。上一章结尾 600 字的承接仍然保留。
- 验收：构造 51 章样例后，生成第 51 章时提示词包含第 50 章摘要和更早的相关未回收伏笔，不含无关伏笔，且注入上下文不超过预算。全量 RAG 仍未做。节点级工作流已在 M2 完成。

### M2. 节点级工作流执行引擎（已完成）

- 状态：已实现。工作流按依赖顺序逐个执行节点，不再把所有节点拼进一次模型调用。`context` 不调用模型，其文本交给下一个节点；`generate` 和 `review` 每次访问各调用一次，后一个节点的提示词包含前一个节点的结果。
- 审稿只区分通过 / 不通过。不通过时退回前一个生成节点，并把审稿意见写入新的提示词，最多返回 2 次；再失败则停止，并写在任务上。这不是按关键事件逐条核对的审稿清单，不要求逐字引文，也不检查连续性。清单在 M3。
- 输出节点沿用原有写入规则：人工审核留下待审核提案且不改正文，自动写入改正文，演示模式不自动写入。普通批量生成仍是每章一次调用。章节记忆、上下文预算和上一章结尾 600 字保持不变。
- 任务事件记录每个节点的开始和结束（成功、失败或取消）。执行中取消会停住当前节点，且不启动后续节点。生成器报错后，重试只重跑失败节点，已成功节点从任务快照里跳过。这与「只重试没有成功提案的章节」是两条路径。
- 内置模板：「章节起草」「起草 → 审稿 → 修改」「只润色」，走同一条创建和运行路径。
- 仍未做：按节点选择模型（M4）、全文检索（M5）、结构化角色表和连续性检查。关键事件审稿清单已在 M3 完成。

### M3. 审稿与连续性检查

- 审稿清单（已完成）：从生成任务入口发起，任务种类是 `review`，不执行工作流节点，不改正文，也不创建章节提案。蓝图「关键事件」的每个非空行是一条。结果只能是已完成、未完成或待核实，并带模型给出的引文和位置。已完成仅当引文是当前正文的逐字子串；模糊、缺字或不是逐字子串时存成待核实。模型语义判断和逐字核对分开保存，引文对得上不会单独变成已完成。模型写成已完成或通过但引文不是逐字子串时，存成待核实，语义判断仍保留。模型标明未完成，或漏掉该条时，该条为未完成。没有非空关键事件时任务完成并给出空清单。生成器报错时任务失败，不留下成功清单。
- 与工作流的区别：工作流 `review` 节点只产出通过 / 不通过，并据此退回生成。那个分支不是这份清单。
- 仍未做：
  - 结构化角色表：人物的称谓、年龄、能力、立场随章节变化，与知识图谱关联，生成与审稿时引用。
  - 连续性检查：时间线、人物状态、设定冲突的提示（仅提示，不自动改稿）。
- 参考：`ck/AI-Novel-Writer-master/docs/plans/chapter-goal-review-production.md`、`docs/adr/0007`、`0017`；`ck/luobi-ai-writing-main/src/services/narrative-consistency`。
- 验收：漏写关键事件、伪造引文、无关键事件、模型失败已有回归用例。机械核对与语义判断分开呈现，不把「引文存在」等同于「已完成」。

### M4. 多模型与用量管理

- 短期已补：单个全局 OpenAI 兼容 Provider 可在 UI 中配置并测试连接，运行时即时生效；该设置写入本机 `.env`，不等同于本阶段的多供应商管理。
- 内容：
  - 模型配置入库：供应商、Base URL、密钥（加密存储、接口不回显）、默认模型、可用模型列表。
  - 按作品或按工作流节点选用不同模型（例如起草用大模型，摘要用小模型）。
  - 「测试连接」与能力检测（流式、结构化输出、上下文长度）。
  - token 用量与估算费用按任务、作品、用户统计。
  - 提示词模板管理：内置模板 + 自定义，区分「内置 / 自定义 / 已修改」状态。
- 参考：`ck/cherry-studio-main`、`ck/lobehub-canary` 的供应商管理；`ck/NovelForge-main` v0.9.6 的模型能力检测与 v0.9.7 的内置项状态。
- 验收：在界面添加第二个供应商后，新任务可选用；用量页与任务事件中的 token 数一致。

### M5. 轻量检索（RAG）

- 动机：参考资料、世界观文档、前文原文无法全部塞进提示词。
- 内容：
  - 导入参考文本，按段落切分；先用 SQLite FTS5 做关键词检索，再视需要加嵌入向量。
  - 嵌入向量按「项目 + 模型版本」隔离，更换嵌入模型需重建索引（参考 `ck/AI-Novel-Writer-master/docs/adr/0004-versioned-project-embedding-space.md`）。
  - 检索结果带来源与引用回执，前端可查看「这段上下文来自哪里」。
- 技术选型原则：优先沿用 SQLite（FTS5、或应用层余弦相似度）保持单二进制部署；只有数据量证明不够时才评估独立向量库（`ck/milvus-master` 仅作规模化时的参考，不作为默认依赖）。
- 验收：导入约 100 万字资料后，检索延迟与相关性在可接受范围内（具体阈值在实现前用样例数据确定）。

### M6. 写作辅助与统计

- 内容：选段局部改写 / 润色 / 扩写，结果仍以提案形式（可 diff）；按章节、作品、日期的字数统计、写作目标与进度；章节与作品级全文搜索；版本记录的两版对比。
- 参考：`ck/luobi-ai-writing-main` 的 Rewrite / Refine 与统计服务。
- 验收：局部改写不改动选区以外的文字；统计与正文字数一致。

### M7. 账户与安全完善

- 内容：修改密码、找回密码（邮件或管理员重置）、邮箱验证；会话列表与远程登出；成员邀请（邀请链接或邀请码）代替「直接按邮箱添加」；生成接口按用户的配额与并发限制；关键写操作审计日志。
- 验收：移除成员后其会话立即失去对应工作区访问权；审计日志可按作品、用户检索。

### M8. 前端架构升级

- 内容：引入路由与状态管理，按领域拆分模块；编辑器升级（可选 CodeMirror 6，支持大章节性能、查找替换、专注模式）；深色模式与响应式布局；无障碍与键盘快捷键。
- 验收：5 万字章节输入无明显卡顿；主路径 E2E 覆盖率达到可回归水平。

## 长期规划

### L1. 多人协作

- 评论与批注（按正文区间）、审阅流程（提交审阅 → 批注 → 通过 / 退回）、活动流。
- 是否做实时协同编辑需要在中期用真实使用数据判断；如做，优先评估 CRDT 方案，并保留现有版本记录作为兜底。

### L2. 多格式导入导出与发布

- 导入：TXT / Markdown / DOCX，自动按章节标题切分。
- 导出：DOCX / EPUB / PDF，支持排版模板与封面；可选对接外部发布平台的稿件格式。
- 参考：`ck/koodo-reader-dev` 的格式处理思路，`ck/luobi-ai-writing-main` 的导出服务。

### L3. 插件与自动化

- 工作流触发器（定时、章节状态变化、应用提案后）；Webhook 通知；开放 API Token，方便与外部脚本集成。
- 工作流模板市场 / 分享导入导出（JSON）。
- 自然语言生成工作流（参考 `ck/NovelForge-main` 的 Workflow Agent），需建立在 M2 之上。

### L4. 创作 Agent

- 对话式灵感助手：可引用章节与实体，调用受控工具（查询图谱、创建实体、提出章节修改提案）；所有写入仍走提案审核，不绕开人工确认。
- 参考：`ck/NovelForge-main` 灵感助手、`ck/AI-Novel-Writer-master/docs/adr/0008-agent-actions-use-domain-fact-and-workflow-seams.md`。
- 前置条件：M1（记忆）、M3（审稿）、M4（多模型与用量控制）已稳定。

### L5. 部署形态与数据

- 可选 PostgreSQL 后端（适配多实例部署）；对象存储保存附件与导出文件；定时备份与一键恢复。
- 本地优先的桌面封装（可评估 Wails 或 Electron，参考 `ck/AI-Novel-Writer-master`、`ck/luobi-ai-writing-main`），让不会部署的作者也能使用。
- 是否做这一步取决于目标用户是「团队自部署」还是「个人作者」，需要在中期确认。

### L6. 评测与质量闭环

- 建立一套合成中文样例与金标准，用来回归提示词与工作流改动：机械检查（格式、字数、引文可定位）、一致性检查、人工文学评分分开记录，避免用改金标准来「通过」。
- 参考：`ck/AI-Novel-Writer-master/docs/experiments/continuity-calibration-round01.md`。

## 协作与认领约定

参考 `ck/NovelForge-main/后续规划.md`：

1. 认领前先建 Issue，说明要做的规划项、实现思路与不做的范围。
2. 标题格式建议：`【功能认领】【模块】名称`、`【方案讨论】【模块】主题`，例如 `【功能认领】【工作流】节点级执行引擎`。
3. 涉及数据模型、权限、模型调用边界的改动，先写一页决策记录（ADR）再动手。
4. 功能完成并合并后关闭对应 Issue，并更新本文档与 README。

## 评审节奏

- 每完成一个短期迭代，回顾本文档：已完成项移到 README 的功能概览，依赖变化的项调整顺序。
- 中期项开工前，先用真实作品（至少一部 50 章以上）验证痛点是否真实存在，再决定是否立项，避免做出没人用的能力。
