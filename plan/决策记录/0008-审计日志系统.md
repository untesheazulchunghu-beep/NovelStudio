# ADR 0008: 审计日志系统

## 状态

已实施 (2026-10-04)

## 背景

系统缺乏对关键操作的追溯能力，无法回答以下问题：
- 谁在什么时间应用了哪个提案？
- 哪些章节被删除了，是谁删除的？
- 用户进行了哪些配置更改？

这在多用户协作环境中尤为关键，需要建立审计追踪机制。

## 决策

实现了基于数据库的审计日志系统，记录所有关键操作。

### 审计日志表结构

```sql
CREATE TABLE audit_logs (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    novel_id TEXT,
    action TEXT NOT NULL,
    target_type TEXT NOT NULL,
    target_id TEXT NOT NULL,
    metadata TEXT NOT NULL,  -- JSON格式
    created_at TEXT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (novel_id) REFERENCES novels(id) ON DELETE CASCADE
);

CREATE INDEX idx_audit_logs_novel ON audit_logs(novel_id, created_at DESC);
CREATE INDEX idx_audit_logs_user ON audit_logs(user_id, created_at DESC);
CREATE INDEX idx_audit_logs_action ON audit_logs(action, created_at DESC);
```

### 支持的操作类型

**Action (操作类型)**：
- `apply_proposal` - 应用提案
- `delete_chapter` - 删除章节
- `delete_novel` - 删除作品
- `restore_chapter` - 恢复章节
- `restore_novel` - 恢复作品
- `create_workflow` - 创建工作流
- `delete_workflow` - 删除工作流
- `update_settings` - 更新设置
- `export_novel` - 导出作品
- `import_reference` - 导入参考资料
- `delete_reference` - 删除参考资料
- `change_provider` - 更改模型提供商

**TargetType (目标类型)**：
- `proposal` - 提案
- `chapter` - 章节
- `novel` - 作品
- `workflow` - 工作流
- `settings` - 设置
- `reference` - 参考资料
- `provider` - 模型提供商

### API 接口

```
GET /api/v1/novels/{novelID}/audit-logs
```

**查询参数**：
- `limit` (int, 1-100, 默认 50) - 返回条目数
- `offset` (int, ≥0, 默认 0) - 分页偏移
- `action` (string, 可选) - 按操作类型过滤
- `user_id` (string, 可选) - 按用户过滤

## 权衡

### 优点

1. **完整追溯能力** - 所有关键操作都有记录
2. **多用户协作支持** - 可以查看谁做了什么
3. **问题排查** - 出现问题时可以追踪操作历史
4. **合规性** - 满足审计要求

### 缺点

1. **存储开销** - 每个关键操作都写入一条记录
2. **性能影响** - 每次关键操作需要额外的 INSERT（约 1-2ms）
3. **隐私考虑** - 记录用户所有操作

### 缓解措施

1. **索引优化** - 在 `novel_id`、`user_id`、`action` 上建立索引
2. **事务内记录** - 使用 `LogTx` 避免额外事务开销
3. **可选清理策略** - 未来可实现定期归档旧日志（如 90 天后归档）
