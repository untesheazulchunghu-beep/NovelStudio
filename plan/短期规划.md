# 短期规划

范围：约 4–6 个迭代（每个迭代为一个可独立合并、可验证的小版本），目标是**修复已确认的 P0 问题、补齐最影响日常写作的缺口、建立工程底线**。
问题背景与代码位置见 [需要改进的内容](./需要改进的内容.md)，编号沿用该文档；更远的方向见 [中长期规划](./中长期规划.md)。

## 原则

1. 先修「会损坏作品或误导用户」的问题，再做新功能。
2. 每项工作都带验收条件；后端改动先写失败的测试再修复，项目已有 `go test ./...` 基础设施。
3. 不引入新的重量级依赖（如向量库、消息队列）；保持「Go 单二进制 + SQLite」的部署形态。
4. 每个迭代结束前执行：`cd backend && go vet ./... && go test ./...`、`cd frontend && npm run build`。
5. 保持向后兼容：旧数据库启动时自动迁移，不要求手动操作。

## 暂不做（明确排除）

- 向量检索 / RAG、多供应商管理、按节点选模型、结构化角色表与连续性检查：放入 [中长期规划](./中长期规划.md)。节点级工作流执行已在 M2 完成。按关键事件逐条核对的审稿清单已可用；它不是工作流 `review` 节点的通过 / 不通过分支。
- 多人实时协同编辑（OT / CRDT）：当前只有乐观锁版本控制，协同编辑成本高，暂不纳入。
- 移动端原生应用：先保证响应式 Web 可用。

## 完成定义（每项任务）

1. 有针对性测试（后端）或可复现的手工验证步骤（前端）。
2. `go vet`、`go test`、`npm run build` 通过。
3. README / `.env.example` 同步更新。
4. 新增用户可见行为时，在 README 「功能概览」或「主要 API」中体现。
